## T65. ユーザーの招待と権限管理

状態: `done` (2026-11-12)

### ゴール

- 管理者が、管理画面から 2 人目以降のユーザーを追加できる (これまでは最初の 1 人しか作れず、著者ページ・操作ログ・編集者権限が活きなかった)。
- 権限 (管理者 / 編集者) の変更、パスキーをなくした人への再登録リンクの発行、ユーザーの削除ができる。

### 仕様

- **招待**: 名前・メールアドレス・権限を入れると、ユーザーを作り、7 日間有効・1 回限りの登録リンク (`/admin/passkey-link?token=…`) を返す。相手はリンクを開いてパスキーを作るとログインできる。リンクは画面に一度だけ表示し、コピーして渡す。
- **再発行**: 既存ユーザーに登録リンクを出し直せる (招待の期限切れ、パスキーの紛失)。出し直すと、そのユーザーの古いリンクは無効になる。自分以外のユーザーの復旧に CLI (`pnpm passkey:link`) が要らなくなる。
- **権限の変更と削除**: ログインできる管理者 (パスキーを持つ管理者) の最後の 1 人は、編集者に下げることも削除することもできない (判定は 1 文で行い、同時操作でも 0 人にならない)。自分自身は削除できない。削除するとそのユーザーのセッション・パスキーは消え、投稿の著者は「なし」になる。削除時に、投稿を別のユーザーへ引き継ぐこともできる。
- **API** (管理者のセッションだけ。API キーは不可): `GET /api/v1/users`、`POST /api/v1/users`、`PATCH /api/v1/users/:id`、`POST /api/v1/users/:id/link`、`DELETE /api/v1/users/:id?reassignTo=`。
- **管理画面**: `/users` (管理者だけに表示)。一覧 (名前・メール・権限・パスキーの数 / 招待中)、招待フォーム、権限の変更、リンクの再発行、削除。
- 編集者ができないこと (これまでどおり): 設定、API キー、サンプルサイト、ユーザー管理、生 HTML ブロック、設定のエクスポート / インポート。

### 完了条件

- 4 ゲート green。実サーバーで、招待 → リンクでパスキー登録 → 編集者としてログイン → 設定 API が 403、を確認する。

### 決定

- 招待は「パスキーを持たない `users` 行 + `passkey_links` 行 (7 日)」。登録は Phase 6 の `/api/v1/auth/passkey-link` をそのまま使い、公開エンドポイントは増やしていない。ユーザーの作成とリンクの発行は 1 つの `db.batch()`。
- API はトークンだけを返し、リンクの URL は管理画面が組み立てる。パスキーは作ったドメインに紐づくので、管理者がいまログインしている origin で登録してもらう必要があるため。
- **「ログインできる管理者が必ず 1 人残る」**: 降格と削除の UPDATE / DELETE の WHERE に「ほかに、パスキーを持つ管理者がいる」を入れた。招待しただけでまだ登録していない管理者は数えない。最初は「ほかに管理者がいる」だけを見ていたが、管理者を招待した直後 (相手が未登録) に自分を編集者へ下げると、設定を開ける人も、リンクを出し直せる人もいなくなるので直した。
- 自分を編集者にする操作は確認ダイアログを挟み、成功したらダッシュボードから読み込み直す (メニューと画面の権限を取り直す)。断られたときは理由を画面に出す。
- 著者ページのスラッグは名前から作る。同じ名前は `-2`、`-3`…。英数字にならない名前 (日本語だけなど) は `user`、`user-2`…。
- 削除: セッション・パスキー・登録リンクは外部キーの cascade で消える。投稿の著者は、引き継ぎ先か「なし」に同じ batch で書き換える。操作ログ・リビジョン・共有リンクに残る `user_id` は NULL になる (履歴の行は残る)。
- API キーでは使えない (`requireRole('admin')` はセッションだけを通す)。招待・権限変更・リンク発行・削除は操作ログに残る。
- 実サーバーのクエリ数: 招待 8、一覧 4、リンクからの登録 6、権限変更 7、リンクの再発行 6、削除 7。編集者でログインして設定 API とユーザー API が 403、管理者に上げた次のリクエストから 200、削除後はセッションが 401。
- テスト: `apps/server/src/api/users.test.ts` (実 DB、9 件)。

## T66. 定期処理 (Cron Trigger)

状態: `done` (2026-11-12)

### ゴール

- ゴミ箱・期限切れの共有リンク・期限切れのセッションなどが、溜まり続けない。

### 仕様

- Worker に `scheduled` ハンドラを足し、`wrangler.jsonc` の `triggers.crons` で 1 日 1 回 (日本時間の未明) 動かす。
- 1 回の実行で行うこと (すべて 1 つの `db.batch()`):
  - ゴミ箱に入って 30 日を過ぎた固定ページ・投稿を完全削除する (リビジョンと共有リンクも一緒に)。
  - 期限切れの共有リンク、セッション、パスキー登録リンク、認証チャレンジを削除する。
  - 400 日より古いアクセス解析の行を削除する。
- ゴミ箱から何か消したときだけ、操作ログに 1 行残す (操作者は `system`)。
- 管理画面のゴミ箱に「30 日後に自動で完全削除されます」と表示する。

### 完了条件

- 4 ゲート green。実 DB のテストで各項目を確認。実サーバーで `scheduled` を手動で呼び、クエリ数を記録する。

### 決定

- `scheduled` ハンドラ (`apps/server/src/scheduled.ts`) が `kanso.housekeeping.run()` を呼ぶ。削除は 11 文を 1 つの `db.batch()` にまとめたので、量にかかわらず 1 クエリ。ゴミ箱から何か消したときだけ操作ログを 1 行足す (操作者 `system`)。テストで「片付けるものがないとき 1 クエリ、あるとき 4 クエリ以下」を固定した。
- 実行は `0 18 * * *` (UTC) = 日本時間 03:00。Workers Free でも Cron Trigger は使える (1 アカウント 5 個まで)。
- 保持期間: ゴミ箱 30 日 (`TRASH_RETENTION_DAYS`。管理画面のゴミ箱の説明と同じ定数)、アクセス解析 400 日 (前年同月と比べられる長さ)。期限切れの共有リンク・セッション・登録リンク・認証チャレンジはその場で消す。
- 親子のページ: ゴミ箱へ入れるとき、生きている子孫も同じ文で入る。そのため期限を過ぎたページに、公開中の子が残っていることはない。
- メディアは消さない (ページや投稿の削除とは独立)。
- ローカルでは Cron Trigger は自動では動かない。`curl http://localhost:5173/cdn-cgi/handler/scheduled` で手動実行できる (README に記載)。
- 実サーバー: 40 日前に捨てたページが消え、昨日捨てたページは残り、操作ログに「ゴミ箱を自動で整理 (固定ページ 1 件・投稿 0 件を完全削除)」が 1 行。
- テスト: `packages/core/src/services/housekeeping.test.ts` (4 件)、`apps/server/src/scheduled.test.ts` (2 件)。

## T67. 画像の最適化

状態: `done` (2026-11-12)

### ゴール

- 公開ページの画像が、表示サイズに合った大きさで配信される。元の大きな画像をそのまま読ませない。
- 画像の幅と高さが HTML に入り、読み込み中にレイアウトがずれない。

### 仕様

- **縮小版**: アップロード時に、ブラウザが幅 480 / 960 / 1600px の WebP を作り (元画像より小さい幅だけ)、元画像と同じ R2 バケットに `<元のキー>.w<幅>.webp` で保存する。行は `media.variants_json` に持つ。対象は JPEG / PNG / WebP (GIF はアニメーションが失われるので対象外)。
- **API**: `PUT /api/v1/media/:id/variants` (multipart。`w480` / `w960` / `w1600` に 1 枚ずつ)。形式、幅が指定どおりであること、縦横比が元画像と合うことを検証する。
- **既存の画像**: メディア画面に「縮小版を作成」ボタン (未作成の画像をまとめて処理)。サンプルサイトの画像もこれで作れる。
- **公開側**: 本文の `<img>`、投稿のカバー画像、セクションの画像、カスタムフィールドの画像、著者のアバターに `srcset`・`sizes`・`width`・`height`・`loading="lazy"`・`decoding="async"` を付ける。本文の画像は保存済みの HTML を表示時に書き換えるので、既存の記事も保存し直さずに効く。
- 縮小版のない画像は、これまでどおり元画像だけを出す。
- メディアを削除すると、縮小版も R2 から消す。
- AI の alt 生成は、縮小版があればそれを使う (元画像が 4MB を超えていても作れる)。

### 完了条件

- 4 ゲート green。実サーバーで、画像をアップロードすると縮小版が R2 に保存され、公開ページの `<img>` に `srcset` が付くことを確認する。公開ページのクエリ数を記録する。

### 決定

- **API は 1 リクエストにまとめた** (仕様の初案は幅ごとに 1 リクエスト): `PUT /api/v1/media/:id/variants` に `w480` / `w960` / `w1600` を multipart で送る。往復が 1 回で済み、3 種でも 5 クエリ。送り直すと前の組を置き換え、使わなくなったファイルは R2 から消す。
- 形式は WebP。WebP を書き出せないブラウザでは、元が JPEG のときだけ JPEG で作る。PNG は透過があるので JPEG にはしない (その場合は縮小版なし)。GIF (アニメーション) と AVIF は対象外で、元画像をそのまま出す。
- サーバーは画素をデコードしない (Workers の CPU 時間に収めるため)。ファイルの先頭だけを読み、形式、幅が宣言どおりであること、元画像より小さい決まった幅であること、縦横比が元画像と合うこと (誤差 2% まで) を確かめる。1 枚 4MB まで。
- スマートフォンの縦向き写真 (EXIF の回転): `readImageSize` が JPEG の Orientation を読み、表示される向きの幅・高さを保存するようにした。以前に保存した行は回転前の寸法を持っているので、縮小版は 90 度回した形も受け付ける。
- 縮小はブラウザの canvas で、半分ずつ段階的に行う (一度に大きく縮めると細部が荒れるため)。品質 0.82。縮小版の作成に失敗しても、元画像のアップロードは成功のまま (あとでメディア画面の「縮小版を作成」で作れる)。
- 公開側: カバー画像・ヒーロー・画像 + テキスト・カスタムフィールドは `ResponsiveImg`。本文は保存済みの HTML の `<img>` を表示時に書き換える (画像のある本文で +1 クエリ、ない本文は 0)。`sizes` は本文カラムの最大幅 42rem に合わせた。カバー画像とヒーロー画像は最初に見える画像なので `fetchpriority="high"` にして lazy にしない。
- 生 HTML ブロックの `<img>`: 引用符の中の `>` でタグを切らないように読む。自分で `srcset` や `width` を書いてある画像には足さない。
- 縮小版を送っている間に元画像が削除された場合、保存した縮小版を R2 から消して 404 を返す (どこからも参照されないファイルを残さない)。
- AI の alt 生成は、幅 960px 以上で一番小さい縮小版 (なければ一番大きい縮小版) を送る。元画像が 4MB を超えていても作れる。
- **投稿の本文の画像がカラムからはみ出していた** (以前からの不具合。`max-width: 100%` が固定ページの `.page img` にしかなかった)。`.post-body img` にも同じ指定を足した。`width` / `height` 属性と `height: auto` の組み合わせで、読み込み中のずれもない。
- 実サーバーのクエリ数: アップロード 5、縮小版の保存 5、画像のある公開ページ 11 (画像なしより +1)、メディアの削除 6 (縮小版も R2 から消える)。
- ブラウザでの確認: 2000×1000 の画像が、幅 1280px の画面では 672px のカラムに収まり 960px 版を、幅 390px・3 倍密度の画面では 1600px 版を読み込む。横スクロールは出ない。
- テスト: `packages/core/src/services/media.test.ts` (9 件)、`apps/server/src/site/images.test.ts` (8 件)。

## T68. Phase 7〜12 の機能の E2E

状態: `done` (2026-11-12)

### ゴール

- Phase 7 以降に足した主な機能が、ブラウザから通しで動くことを CI が毎回確かめる。

### 仕様

- 追加するシナリオ: ゴミ箱へ移動 → 復元、下書きの共有リンク (ログアウト状態で開ける・無効化で 404)、メニュー (ヘッダーが差し替わる)、エクスポート → インポート、ユーザーの招待 → 登録リンクでログイン、画像のアップロード → 縮小版 → 公開ページの `srcset`。
- 既存の方針どおり、作ったものは `e2e-` の接頭辞で作り、終わったら消す (メニューはスラッグが決まっているので、名前を `E2E ` で始める)。

### 完了条件

- 新しい DB と開発用 DB の両方で `pnpm e2e` が全部通る。

### 決定

- `e2e/operations.spec.ts` に 7 シナリオ: ゴミ箱へ移動 → 復元、下書きの共有リンク (ログアウト状態で開ける・無効化で 404)、ヘッダーメニュー、エクスポート → 完全削除 → インポート、ユーザーの招待 → リンクで登録して編集者としてログイン、招待した管理者が自分を編集者に下げる、画像のアップロード → 縮小版 → 公開ページ (固定ページと投稿の両方で `srcset`・寸法・カラムに収まること)。E2E 全体は 12 件。
- **新しい DB と開発用 DB の両方で 12/12。**
- 開発用 DB で見つかった不具合: 自分のサイトのエクスポートをそのまま取り込み直すと「更新 1 件」になり、リビジョンが 1 つ増えた。古い版が抜粋を空文字で保存していた行を、「抜粋なし (NULL)」と違うものとして扱っていたため。比較をそろえた (抜粋の空文字は「なし」と同じ。投稿のカスタムフィールドは、いまの定義で保存し直した形と比べる — 投稿タイプにあとからフィールドを足した場合も「変更なし」になる)。`transfer.import.test.ts` に回帰テストを追加。
- 片付け: `e2e-` で始まる固定ページ (ゴミ箱の中も)・投稿タイプとその投稿・ユーザー・メディア・フォーム、名前が `E2E ` で始まるメニューを、前後に消す。完全削除は `force=true` (Phase 11 で DELETE がゴミ箱移動だけになったため)。
- ヘッダーメニューのシナリオは、`header` メニューがすでにある DB ではスキップする (利用者のメニューを書き換えない)。
- パスキーの仮想認証器 (`addVirtualAuthenticator`) は `e2e/helpers.ts` に移して共有した。
