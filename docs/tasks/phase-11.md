## T60. ゴミ箱の完全削除条件、LIKE 50 バイト制限、リダイレクト CSV

状態: `done` (2026-11-12)

### ゴール

- 二重クリックや通信の再送で、ゴミ箱を素通りして完全削除にならない。
- パスや検索語が長くても 500 にならない。
- リダイレクトの CSV を画面に書いてある上限 (500 行) まで取り込める。

### 仕様

- `DELETE /pages/:id`・`/posts/:id` は、`?force=true` のときだけ完全削除する。ゴミ箱にある行への `force` なしの DELETE は何もせず 200 を返す (T46 の「2 回目以降は行削除」を取り消す)。
- ゴミ箱への移動で子孫を巻き込む条件を、`like 'パス/%'` から前方一致の比較 (`substr(path, 1, n) = 'パス/'`) に変える。D1 は LIKE のパターンを 50 バイトに制限しており、パスが 49 バイト以上で子ページがあると 500 になっていた。
- 一覧の検索 (固定ページ・投稿・メディア・リダイレクト・タグ) を `like '%語%'` から `instr(lower(列), lower(?)) > 0` に変える。17 文字以上の日本語で 500 になっていた (Phase 5 から残っていた不具合)。
- リダイレクトの CSV インポート: 既存行の確認を `in (...)` 1 回 (最大 500 個のバインド変数) から、既存の `from_path` を 1 回で読む形に変える。D1 のバインド変数は 1 クエリ 100 個まで。

### 完了条件

- 4 ゲート green。実サーバーで、長いパス + 子ページのゴミ箱移動、DELETE 2 回、21 文字の日本語での一覧検索、500 行の CSV がすべて成功する。

### 決定

- `db/search.ts` に `contains()` (`instr(lower(列), lower(?)) > 0`) と `startsWith()` (`substr(列, 1, n) = ?`) を置き、5 つの一覧検索とゴミ箱の巻き込みを置き換えた。大文字小文字の無視は ASCII のみ (LIKE と同じ)。`%` と `_` は普通の文字として扱う。
- LIKE の制限は「行に対して LIKE が評価されたとき」にだけ発動する。子ページがないと通り、あると 500 になっていた。空のテーブルでは再現しないので、テストは一致する行を置いて行う。
- `DELETE` は `force=true` のときだけ完全削除する。ゴミ箱にある行への `force` なしの DELETE は何もしない。
- リダイレクト CSV は既存の `from_path` を 1 クエリで全件読む。
- 実サーバー: 61 文字のパス + 子ページのゴミ箱移動が 200 (6 クエリ)、2 回目の DELETE 後も親子ともゴミ箱に残る、`force=true` で完全削除、21 文字の日本語での検索が 5 種すべて 200、CSV 500 行が 200 (10 クエリ)。
- テスト: `services/trash.test.ts` (実 DB)。

## T61. 操作ログ: ログイン失敗の集約

状態: `done` (2026-11-12)

### ゴール

- ログインしていない第三者が、操作ログを失敗の記録で埋めて本物の履歴を押し出せない。

### 仕様

- `activity_log` に `count` 列 (既定 1) を足す。ログイン失敗は 1 時間ごとに 1 行へまとめ、同じ時間帯の 2 回目以降は `count` を増やすだけにする。
- 管理画面の一覧は `count > 1` のとき回数を表示する。

### 完了条件

- 4 ゲート green。実サーバーで失敗を 5 回送っても、ログの行が 1 行しか増えない。

### 決定

- マイグレーション `0016_activity_count.sql` (`count integer DEFAULT 1 NOT NULL`)。
- `activity.logFailedSignIn()`: 直近 1 時間の `login_failed` 行があれば `count + 1` するだけ (1 クエリ)、なければ通常どおり 1 行足す。ログの書き込みに失敗しても、ログインのエラー (401) をそのまま返す。
- 実サーバー: 失敗 5 回でログの行は 1 行だけ増え、`count` は 5。失敗 1 回あたり 3 クエリ。
- テスト: `services/activity.test.ts` (実 DB)。失敗 50 回でも 1 行、1 時間を過ぎたら新しい行、上限 2,000 行の切り詰め。

## T62. アクセス解析の計測位置とグラフ

状態: `done` (2026-11-12)

### ゴール

- キャッシュから返したアクセスも数える。管理者自身の閲覧は数えない。
- データが少ない時期でもグラフが普通の大きさで表示される。

### 仕様

- 計測のミドルウェアを `siteCache` の手前に移す (キャッシュから返すと後ろのミドルウェアは実行されないため、5 回の閲覧が 1 回と記録されていた)。
- セッション Cookie が付いたリクエストは数えない (これまでは逆に毎回数えていた)。
- 日付の区切りに使うタイムゾーンの読み出しは、アイソレートごとに 60 秒だけ覚えておく (1 閲覧あたりの D1 クエリを 2 回から 1 回にする)。
- `analytics.summary()` は期間内の全日を返す (閲覧のない日は 0)。グラフは常に期間の日数ぶんの軸で描く。

### 完了条件

- 4 ゲート green。実サーバーで、匿名の 5 回が 5 と記録され、ログイン中の閲覧は増えない。データが 1 日分でもグラフの高さが変わらない。

### 決定

- 計測を `middleware/pageviews.ts` に分け、`siteCache` の前に登録した。除外するパスは `/search` と `/preview` をパスの区切りで判定する (これまでは `search` で始まるパス全部を除外しており、`/search-tips` のようなページが数えられていなかった)。
- セッション Cookie が付いたリクエストは数えない。
- タイムゾーンはアイソレートごとに 60 秒覚える。キャッシュから返した閲覧 1 回あたりの D1 クエリは 2 (キャッシュの世代 + カウント)。
- `summary()` は `analyticsDayKeys()` で期間内の全日を返す。UTC 正午を基準に日付を刻むので、夏時間の切り替え日でも欠けや重複が出ない。グラフは日数ぶんの固定幅になり、データが 1 日分でも高さは変わらない (修正前は約 8,000px)。
- 実サーバー: 匿名の 5 回 (キャッシュなし 1 + キャッシュから 4) が 5、ログイン中の 3 回は 0。
- テスト: `middleware/pageviews.test.ts` (Worker 全体 + 実 DB + キャッシュの差し替え)、`services/analytics.test.ts`。

## T63. エクスポート/インポートの安全化と一括処理

状態: `done` (2026-11-12)

### ゴール

- 別のサイトから取り込んだあと「サンプルを削除」しても、無関係のコンテンツが消えない。
- 管理者だけが変えられる設定を、インポート経由で書き換えられない。
- Workers Free の 50 クエリに収まる。
- フォームの定義も持ち運べる。

### 仕様

- **設定キー**: `starter` (サンプルの行 ID 一覧) と `cache` (キャッシュの世代) は、そのサイトだけで意味を持つ値なので、エクスポートにもインポートにも含めない。インポートに入っていたら警告を出して読み飛ばす。
- **権限**: `GET /export?settings=1` と、インポートでの設定の適用は、管理者のセッションだけに許す。設定 API (`requireRole('admin')`) と同じ条件。権限のないインポートは設定だけ読み飛ばして警告を出す。
- **順序**: 設定は最後に適用する (`notFoundPageId` が、同じインポートで作ったページを指せるようにする)。
- **フォーム**: バンドルに `forms[]` (slug・名前・項目・通知先・完了メッセージ・リダイレクト先・Turnstile) を足す。送信データは個人情報なので含めない。
- **一括処理**: 1 件ずつサービスを呼ぶのをやめ、「必要な行をまとめて読む → メモリ上で差分を取る → `db.batch()` でまとめて書く」にする (Phase 5 のサンプル投入と同じ方針)。検証 (予約スラッグ、投稿タイプとの衝突、親ページ、カスタムフィールド、メディアの存在) はメモリ上で行い、問題のある項目は警告を出して読み飛ばす。更新した固定ページ・投稿には、これまでどおりリビジョンを残す。
- **1 リクエストの上限**: 固定ページ・投稿は 1 リクエスト 100 件まで。管理画面は大きなファイルを自動で分割して順に送る。
- ページの `path` の各階層を、スラッグの形式で検証する (これまで未検証だった)。

### 完了条件

- 4 ゲート green。実サーバーで次を確認し、クエリ数を記録する。
  - サンプルサイト一式を別のサイトに取り込んで「サンプルを削除」しても、取り込み先の自前のコンテンツが残る。
  - 書き込み用 API キーのインポートでは設定が変わらない。
  - 投稿 100 件の新規インポートと、変更なしの再インポートが 50 クエリに収まる。

### 決定

- **一括処理**: 読み込みは項目数によらず 15 クエリ前後。書き込みは 40 文または約 900KB ごとに `db.batch()` する。同じインポートで作った行への参照 (カテゴリの投稿タイプ、子ページの親、投稿のカテゴリ・タグ) は、文の中の slug / path サブクエリで解決するので、ID を読み戻さない。タグとカテゴリは複数行 INSERT。
- **検証はメモリ上で済ませる**: 予約スラッグ、投稿タイプとページのスラッグの衝突、親ページの有無、カテゴリの循環、カスタムフィールド、ファイル内の重複。問題のある項目は警告を出して読み飛ばし、バッチは失敗させない。同時編集による一意制約違反だけは 409 (「もう一度実行してください」) にする。インポートは upsert なので、途中で止まっても再実行すれば続きから進む。
- **クエリ数** (実サーバー、セッション確認・操作ログ・キャッシュ世代を含む):

  | 内容 | 修正前 | 修正後 |
  |---|---|---|
  | サンプルサイト一式を別サイトへ | 82 (1 リクエスト) | 10 / 8 / 12 / 11 (4 リクエスト) |
  | 投稿 5 件を新規 | 50 | — |
  | 固定ページ 100 + 投稿 100 を新規 (1 リクエスト) | — | 19 |
  | 同じ内容をもう一度 (変更なし) | 54 (52 件) | 17 (200 件) |
  | 投稿 100 件をすべて更新 | — | 27 |

- **1 リクエストの上限** (`IMPORT_REQUEST_LIMITS`): 固定ページ・投稿は 100、タグ・カテゴリ・リダイレクトは 500、それ以外は 100。`splitBundle()` (shared) が「構造 → 固定ページ (親から) → 投稿 → 設定」の順に分割する。管理画面は 50 件ずつ送り、進み具合 (n / m) を出す。
- **設定**: `starter` と `cache` はエクスポートに含めず、インポートに入っていたら警告して読み飛ばす。`GET /export?settings=1` は管理者セッション以外 403。インポートの設定は、管理者セッション以外では読み飛ばして警告する。設定は最後に適用する。
- **フォーム**: `forms[]` を足した。Turnstile が未設定のサイトでは `turnstile: false` にして警告する。
- **画像**: セクションとカスタムフィールドの `image` 型の値を `{ $ref: 'media', key }` で持ち運ぶ。これまでは取り込み元のメディア ID のままで、取り込み先では無関係の画像を指し得た (実サーバーで確認)。セクションの項目定義はテーマのカタログ (server 側) にあるので、API 層が `sectionFieldsOf` を渡す。キーのない素の ID は信用せず外して警告する。
- **実サーバーでの再現確認**: サンプルサイトを入れたサイト A を設定込みでエクスポート (設定キーは `site, theme` だけ) → 自前のページ 6・投稿 4 があるサイト B に取り込み → B の `/api/v1/starter` は `installed: false`、削除 API は 404、自前のコンテンツは全部残った (修正前は自前のページ 4・投稿 3 が完全削除された)。書き込み用 API キーでは `export?settings=1` が 403、インポートの `headHtml` も反映されない (修正前は公開トップに出た)。
- テスト: `services/transfer.import.test.ts` (実 DB、13 件)、`api/transfer.test.ts` (Worker 全体)、`shared/transfer.test.ts` (`splitBundle`)。

## T64. 細かな修正

状態: `done` (2026-11-12)

### ゴール

- レビューで挙がった小さな不具合を片付ける。

### 仕様

- **著者ページ**: その投稿タイプに公開済みの投稿が 1 件もない著者の `/{type}/author/{slug}` は 404 にする (空の一覧が検索エンジンに登録可能な状態で出ていた)。
- **メンテナンスモード**: メッセージが未入力のときの文言を専用に用意する (404 用の文言が出ていた)。
- **フィード**: Atom フィードは固定表示を無視して新しい順に並べる。
- **カスタムフィールド**: 公開側で値の検証に失敗したとき、保存値をそのまま描画するのをやめ、項目ごとに検証して不正な値は出さない。チェックボックスの表示文言 (「あり」) をサイトの言語に合わせる。
- **共有リンクの URL**: `SITE_URL` が `localhost` のときはリクエストの origin で作る (開発中に別のポートで動かすとリンク先が合わなかった)。
- **AI の alt**: ファイル名からの推測をやめ、R2 の画像そのものを画像対応モデルに渡して作る。画像対応モデルが使えない形式 (SVG など) ではボタンを出さない。

### 完了条件

- 4 ゲート green。実サーバーで各項目を確認する (AI は binding をモックした単体テストのみ。実サービスへの接続はユーザーの Cloudflare アカウントを使うため行わない)。

### 決定

- 著者ページは、その投稿タイプに公開済みの投稿が 0 件なら 404。
- メンテナンスの既定文言は `messages.maintenance.body` (日本語・英語)。
- フィードは `listPublished({ order: 'newest' })`。アーカイブは固定表示が先頭のまま。
- カスタムフィールドは項目ごとに検証し、定義に合わない保存値は既定値に落とす (text から url に定義を変えたとき、保存済みの `javascript:` がリンクとして出ないことをテストで固定)。チェックボックスは `messages.post.yes`。
- 共有リンクは `publicOrigin(c)` で作る。`SITE_URL` のホストが `localhost` のときだけリクエストの origin を使う。
- AI の alt: `POST /api/v1/ai/alt { mediaId }`。R2 から画像を読み、base64 の data URI にして `@cf/mistralai/mistral-small-3.1-24b-instruct` に渡す (入力の形は、インストール済みの `@cloudflare/workers-types` の型で確認した)。JPEG / PNG / WebP / GIF・4MB まで。`suggest` の `alt` 種別は削除した。**実サービスでは未確認**。binding をモックしたテストだけで、Workers AI に実際に接続しての確認はしていない (ユーザーの Cloudflare アカウントへの接続と課金を伴うため)。
- テスト: `site/site.integration.test.ts`、`api/ai.test.ts`。全体は seo 13 / create-kanso 47 / shared 104 / core 141 / server 264 / admin 36 = 605 件。
